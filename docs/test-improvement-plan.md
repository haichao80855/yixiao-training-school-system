## 三、问题清单（按严重度）

### P0：会让坏代码直接上线，或破坏数据

**P0-1 没有 CI，也没有部署门禁**
- 证据：仓库没有 `.github/workflows`；`deploy/deploy-to-aliyun.sh` 只做构建，不跑测试。
- 影响：测试是否运行全靠人记得。类型错误、回归缺陷都可能直接上线。
- 建议：建 PR 流水线，部署脚本加一道「测试通过才部署」的检查。

**P0-2 测试默认写开发库，没有环境保护**
- 证据：
  - 测试写死 `3001` 端口；`run_all_unified.cjs` 发现 3001 已有服务就直接复用。
  - 开发服务器用的 `dev.db` 是生产数据快照。
  - `scripts/clear_test_data.cjs`、`cleanup_duplicate_test_courses.cjs` 的存在，说明以前已经出现过污染。
- 影响：
  - 开发库里混进测试数据，用它排查线上问题时会被误导。
  - 测试之间互相干扰，结果时好时坏。
  - 万一指向生产库，就会用超管权限写入数据。
- 建议：一键隔离运行（临时库、随机端口）；加一道保护，库路径或地址可疑时拒绝运行。

### P1：测试结果不可信

**P1-1 三套运行清单互相对不上**
- `AGENTS.md` 规定提交前必须跑 `test:all`，但它只包含 25 个后端测试。下面这些**都不在 `test:all` 里**：
  - 数据隔离安全 `test-data-scope-security.js`、校区切换 `test-campus-switch-scope.js`
  - 老师课酬、站内通知、家长端
  - 生产配置检查
- 结果是：`test:all` 全部通过，并不代表安全和资金相关的测试也通过了。
- 建议：只保留一份清单，由一个运行器读取。新增测试必须加进清单，否则 CI 报错。

**P1-2 分层用例测的是复制品，属于虚假覆盖**
- 证据：
  - `tier1~4` 共 67 个文件，引用的是 `tests/contracts/` 里的手写模型。
  - 这些模型和 `src/utils/financeAggregator.ts`、`rbacEngine.ts`、`collisionEngine.ts` 已经不一致：194 行对 313 行，117 行对 130 行，261 行对 302 行。
  - 有的用例只检查常量，例如 `t1_04_routes_mock.test.js` 断言一个写死的数组长度是 4。
- 影响：「287 项用例全部通过」的报告给人错误的信心，真实回归一个都拦不住。
- 建议：有业务含义的场景改写成调用真实后端，或者直接测试 `src/utils`；只检查常量的用例删除；`tests/contracts/` 整个删除。

**P1-3 前端零测试，而缺陷集中在前端**
- 证据：75 个页面没有任何单元测试；近两周大部分 `fix` 是页面显示和权限可见性问题。
- 风险最高、最容易测的几处：
  - `src/router/access.ts`（`canAccessRoute`，决定菜单显示和路由守卫）
  - `src/layout/AppSidebar.vue` 的菜单配置
  - `src/utils/*`（金额、日期、课包合并、CSV 导出）
  - `src/api/normalizers/*`
- 建议：引入 Vitest，第一批先写权限矩阵测试和工具函数测试。

**P1-4 运行器和报告太简陋**
- 用 `&&` 串联，一个失败就停；没有汇总，也看不出哪些测试慢。
- 每个文件自己写断言和计数逻辑，输出格式各不相同，没法统计。
- 没有覆盖率数据，不知道哪些领域代码完全没被测试执行到。

### P2：有隐患的盲区

**P2-1 请求参数校验既没生效，也没被测**
- 证据：
  - 全局没有启用 `ValidationPipe`，`educational.service.ts:320` 的注释里也写了这一点。
  - 16 个 DTO 文件里写的 `@IsString` 之类的校验其实**都不起作用**。
  - 有 9 处接口直接收 `body: any`。
- 影响：参数类型错误、多余字段、负数金额、超长文本，只能靠业务代码自己挡。现在没有任何「异常输入」测试证明这些都挡住了。
- 建议：先补异常输入测试，摸清现状。启用全局校验是一项**会改变线上行为**的代码改动，要单独评估，不在测试计划里直接做。

**P2-2 并发和重复提交几乎没测**
- 只有 2 个后端测试有并发场景。
- 高风险操作没有并发测试：点名或结课重复提交、审批按钮连点、退费重复审批、续报时抢最后一个名额。
- 建议：对每个「写钱或写课时」的接口，各补一个「同一请求并发 2 次，结果只生效 1 次」的测试。

**P2-3 时区和日期边界只有课酬测过**
- 业务日期统一按北京时间（`toBusinessDateParts`），但只有 `test-teacher-pay.js` 测了跨天边界。
- 课消、到课率、月度统计都没测过这些场景：UTC 16:00 前后、月末最后一天、闰年 2 月。

**P2-4 测试数据依赖种子数据和超管账号**
- 测试默认种子里的账号和班级一定存在，并且大量使用超管账号，所以权限问题反而被掩盖了。
- 建议：每个测试自己造数据、自己清理；能用业务角色（校长、老师、财务）就不用超管。

**P2-5 浏览器端到端测试无人维护**
- `scripts/` 下十几个脚本没有统一入口和统一账号，很可能已经有一部分跑不通。

**P2-6（下个周期）小程序测试**
- 小程序测试加载的是 `mini-program/dist` 构建产物，没先构建就测，测的是旧代码。下个周期改小程序时一并处理。

## 五、目标测试策略

### 5.1 分层（测试金字塔）

| 层级 | 工具 | 测什么 | 运行时机 | 目标耗时 |
|---|---|---|---|---|
| L1 静态检查 | `vue-tsc`、`tsc`、`lint:ui` | 类型、样式规则 | 每个 PR | < 2 分钟 |
| L2 单元测试 | Vitest（前端）；后端 `domain/` 纯函数 | 计算引擎、权限判断、工具函数 | 每个 PR | < 1 分钟 |
| L3 接口集成测试 | 现有 `server/test-*.js` + 新运行器 | 真实接口 + 临时库 | 每个 PR | < 8 分钟 |
| L4 浏览器冒烟 | puppeteer-core（已安装，不引入新框架） | 6 条关键路径 | 每晚一次 + 发版前 | < 10 分钟 |
| L5 线上冒烟 | curl + 只读账号 | 健康检查、登录、关键查询 | 每次部署后 | < 1 分钟 |

### 5.2 环境与数据规范
- **测试只能连临时库。** 运行器自动复制一份种子库到临时目录，在随机端口起后端，跑完删除。
- **环境保护。** 如果 `DATABASE_URL` 指向 `server/prisma/dev.db`、生产路径，或者地址包含 `aiic.space`，测试直接退出。
- **测试数据。** 每个测试用统一前缀 `__t_<随机串>` 自己造数据，结束时按前缀清理；运行器结束后再按前缀检查有没有残留。
- **测试账号。** 种子数据里增加一组专用测试账号（每种角色一个）。测试从同一个配置读取账号密码，不再在 39 个文件里写死。

### 5.3 准入和准出标准
- **PR 能合并的条件：** L1~L3 全部通过；新增后端测试已加入统一清单；`fix` 类 PR 附带一个能复现该缺陷的测试。
- **能部署的条件：** `main` 分支最新一次 CI 通过；部署脚本本地复核类型检查和核心测试。
- **上线完成的标准：** L5 线上冒烟通过；失败时提示用最近的备份回滚。

### 第 2 期：清理虚假覆盖（约 4 个工作日，P1-2、P2-4、P2-5）
- `tier1~4` 逐个处理：
  - 有业务含义的场景改写成接口测试或 `src/utils` 单元测试，例如：钱包先扣赠送金、反结课冲正、跨校区隔离、组合支付。
  - 只检查常量的用例删除。
  - 删除 `tests/contracts/`。
- `tests/` 中不在任何运行器里的 38 个脚本：能跑的纳入清单，过时的删除，并在 PR 里列出每个文件怎么处理的。
