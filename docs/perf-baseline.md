# 接口耗时基线

> 流畅度改进计划 ([perf-improvement-plan.md](perf-improvement-plan.md)) 第 0 期的测量结果。之后每期结束都重跑一次，把新数据加到下面的表里对比。

## 怎么测

```bash
npm run bench                     # 种子数据、scale=1、scale=10 三档
npm run bench -- --scales=1 --runs=20 --out=bench.json
```

- **环境：** `tests/isolated-env.cjs --exec=scripts/bench-api.cjs`：临时库加随机端口的后端，跑完全部删除，不碰 `dev.db`。
- **造数（`scripts/seed-load.cjs`）：** 往执行校长所在校区写入数据，每一档在上一档的基础上累加。
  - scale=1 约等于一个中等校区一年的量：300 名学员（每人一个课包、一笔订单）、25 个班、1000 节排课、约 1.1 万条上课记录。
  - scale=10 是它的 10 倍：3000 名学员、1 万节排课、约 9 万条上课记录。
- **测法：** 每个接口先预热 2 次，再顺序请求 30 次，取 p50 和 p95（单位 ms，本机 → 本机，不含公网延迟）。用执行校长账号，与线上主要使用者一致。
- **后端日志：**
  - 慢请求：≥300 ms 时打 `[timing]` warn。阈值用 `SLOW_REQUEST_MS` 调，`REQUEST_TIMING_LOG=all` 时每个请求都打。
  - 慢查询：≥100 ms 时打 `[slow-query]` warn。阈值用 `SLOW_QUERY_MS` 调。
  - 每个响应都带 `Server-Timing: app;dur=…` 头，浏览器开发者工具的 Network → Timing 里能看到。

## 第 0 期结论 (当时的判断，第 2 期已处理 1、2 两项)

1. **点名工作台快照是头号瓶颈。** 即使只要今天的课（`date=今天`），也会把校区全部上课历史和多层关联一起拉回来，然后在内存里分组。scale=1 时已经 0.85 秒、3.5 MB，scale=10 时 8.6 秒、29 MB，而且和带不带日期无关。点名页（`attendance.vue`）和工作台每次打开都会请求它。这是第 2 期的第一个任务。
2. **排课接口不带日期时，耗时和体积随历史线性增长**（scale=10 时 753 ms、14.5 MB）。带上本周的日期范围后降到 55 ms、213 KB。排课页（`timeSchedule.vue`）目前不带日期，这一项在第 2、3 期处理。
3. **看板和续报名单**在 scale=10 时接近 200 ms。原因是在 JS 里汇总全部记录，第 2 期改用 SQL 聚合。
4. **其余接口**在 10 倍数据下都在 50 ms 以内。主要表加了索引以后，学员列表和订单列表还会再降。
5. **测量方式的局限：** 本机测量，没有并发；SQLite 写锁带来的排队（B-4）不在这张表里，第 2 期压测时会加上并发写的场景。
