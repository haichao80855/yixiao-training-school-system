# 0004. 下沉班级花名册与分班履约为统一深模块

## 状态
Accepted

## 背景与决策
在学员中心与教务中心的日常运营中，班级花名册编排与分班履约是核心高频场景。原系统在该接缝处存在严重的架构摩擦与并发隐患：
1. **班容并发控制缺失**：前端待分班工作台（`unassigned.vue`）使用 `Promise.all(ids.map(...))` 循环并发发起多个单个 HTTP 请求，服务端 `bindStudentToClass` 仅执行平铺自增而无行级排他锁，导致开学季并发分班时极易突破班容上限（`capacity`），造成严重超编与班级人数虚增；
2. **待分班名册数据截断**：前端通过无分页参数的 `studentApi.getStudents({})` 获取全量学员并在浏览器中内存过滤，受限于服务端默认 `pageSize: 10` 的分页截断规则，导致第 11 名之后的待分班学员被物理吞没；
3. **人数守恒与学籍状态撕裂**：学员跨班重编时原班级在读人数未被原子核销，学员主体状态未被推进为 `in_class`；且系统完全缺失“合规移出班级并回退待分班池”的逆向业务接缝。

我们决定在服务端建立学员班级入班协调器深模块 `ClassRosterCoordinator`（以任务型业务方法为主干，融合行级 CAS 并发锁与预演仿真）：
- 对外暴露高杠杆任务型接缝：`assignStudents`（单请求批量分班）、`removeStudent`（合规移出并回退待分班池）、`getUnassignedRoster`（服务端分页聚合大盘）与 `getClassRoster`（花名册全景与低课时预警）；
- 内部在单一 `$transaction` 事务内闭环行级 CAS 条件并发锁（`currentStudentCount + N <= capacity`）、课包课程智能匹配嗅探、原班计数原子冲减、学籍状态机自愈推进；
- 彻底废除前端 `Promise.all` 循环并发与脆弱的浏览器端内存过滤。

## 评估过的备选方案
- **备选方案 A（纯 CQS 双入口泛化命令架构）**：对外仅提供 `execute(command)` 与 `query(spec)`。被否决，对于 95% 以上的前台批量分班和移出班级场景，泛化命令结构体在上层控制器和前端页面徒增了参数装配认知成本。
- **备选方案 B（纯任务型平铺方法）**：仅提供批量分班与移出，不包含零写预演与仿真。虽然调用直观，但在复杂调班排课场景下缺乏点击前的零写副作用班容诊断能力。
- **入选方案（实用主义融合深模块）**：以方案 B 面向核心调用端的高阶任务为主干，内部融合方案 A 的行级 CAS 锁、原班冲减不变量与学籍状态机自愈，并提供可选的零写副作用预演（`dryRun` / `preview`）。

## 结果与收益
- **班容超编事故清零**：数据库行级 CAS 锁在单事务内严格守卫容量上限，彻底杜绝并发超编与人数失真。
- **网络并发降为 $O(1)$**：批量分班由 $N$ 次并发请求缩减为恒定单次请求，杜绝半程脏数据与网络竞争。
- **待分班名册 100% 完整**：服务端直查有效待分班课包（`classId is null`）并分页输出大盘度量，彻底解决 10 条分页截断丢失学员问题。
- **补齐移出班级闭环**：通过 `removeStudent` 首次实现学员安全移出班级、释放班容并优雅回退待分班池。
- **测试表面高度收敛**：测试用例直接面向 `ClassRosterCoordinator` 的 4 大任务方法发起穿透验证，摆脱对 UI DOM 绑定的依赖。
