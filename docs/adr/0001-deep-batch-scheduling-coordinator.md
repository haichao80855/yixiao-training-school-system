# 0001. 下沉循环排课与三维碰撞至服务端排课深模块

## 状态
Accepted

## 背景与决策
排课日程（Schedule）与三维碰撞冲突检测原本在前端 `collisionEngine.ts` 与服务端 `educational.service.ts` 呈现双轨割裂，批量排课在浏览器中循环发起 16~48 次 HTTP 检查与写入请求，不仅容易造成断网后的半程脏数据，且前端无法感知班级跨校区授权与批次内自碰撞。

我们决定在服务端建立高内聚深模块 `BatchSchedulingCoordinator`，对外提供纯内存预演（`preview`）与事务落盘（`commit`）统一接缝，封装实体水化、多维冲突检测（教师、教室、容量、班级、营业窗口与批次内自碰撞）、自适应 4 泳道图染色分配与单一 `$transaction` 原子性保障；前端排课向导组件全面退化为纯呈现表单。

## 评估过的备选方案
- **备选方案 A（纯客户端循环推演）**：保留前端循环调度，仅在后端增强单个日程的碰撞拦截。被否决，因为无法提供原子事务保证（All-or-Nothing），存在严重 N+1 网络风暴。
- **备选方案 B（微规则插件流水线架构）**：将每个碰撞规则拆分为独立类（`TeacherConflictRule`、`ClassroomCapacityRule` 等）。被否决，目前系统 95% 为常规班级规律排课，过早暴露大量细粒度规则类违背 YAGNI 原则，增加了上层调用的装配成本。
- **入选方案（实用主义融合深模块）**：单入口高杠杆 CQS 接口（`preview`/`commit`），内部实现闭环四维碰撞矩阵、反 N+1 预取缓存与单事务写入。

## 结果与收益
- **网络效率**：排课交互从 32~96 次 HTTP 往返骤降为恒定 1 次预演 + 1 次提交。
- **数据一致性**：排课碰撞判定与持久化在服务端单事务内完成，遇冲突严格按仲裁策略（`STRICT_ABORT` 全量回滚 vs `ALLOW_AND_FLAG` 标红跳动高亮）处理，彻底杜绝半程脏数据。
- **测试曲面**：测试端只需跨过 `preview` 与 `commit` 两个入口即可完整覆盖排课全链路，消除对 UI 异步发包的脆弱依赖。
